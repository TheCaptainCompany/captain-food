# ADR-20260802-220402 — Mailbox keyspace width 100 → 5

## Status

Accepted (product-owner directive, 2026-08-02)

## Context

The post-merge audit of
[#301 "feat(#300): push the drain loops from Postgres NOTIFY instead of polling every 1.5s"](https://github.com/TheCaptainCompany/captain-food/pull/301)
found that the actor mailbox is a larger idle-query source than the `domain_events` polling that
PR removed: every owned lane costs one `SELECT ... WHERE status = 'RECEIVED'` per worker pass
even when empty (`MailboxWorker::drain_lane`), the pass runs every 10 s
(`WorkerConfig::default`), the workers are un-gated ("ALWAYS running when a DB is configured"),
and every actor type declared `mailbox.partitions: 100`. 16 actor types × 100 lanes ≈ 1,600 idle
queries per 10 s (~580k/hour) from a single monolith instance — ~8× what #301 eliminated — and
the cost multiplies per process when `RUN_MAILBOX_WORKERS` is enabled in the standalone adapters.

Width is parallelism, not capacity: a partition is the unit of ordered, serialized delivery, and
100-way parallelism per actor type is far beyond Tours-scale V0 (PROP-20260728-152752 §2 chose
100 as a generous default, not a measured need).

## Decision

Reduce `mailbox.partitions` from 100 to 5 for all 16 actor types in `specs/actors.yaml`
(regenerated into `ACTOR_MAILBOXES` / `mailbox_address`). Idle drain cost drops 20× (~80
SELECTs per 10 s); per-actor head-of-line ordering is untouched; delivery parallelism per actor
type becomes 5, still comfortably above V0 peak.

Migration `20260802220000_mailbox_width_100_to_5.sql` remaps stamped rows and shrinks the
registry. The remap is **exact, not approximate**, because 5 divides 100: `stable_partition` is
`fnv1a64(actor_id) mod width` (frozen by golden-value test), and `(hash mod 100) mod 5 ==
hash mod 5` — so `partition % 5` reproduces the width-5 stamp without re-implementing FNV in
SQL. Long-lived SCHEDULED reminders remap with everything else, so nothing strands. Rows are
remapped before registry rows ≥ 5 are deleted; both statements are idempotent, closing the
rolling-deploy window (a width-100 writer inserting after the migration strands a row only until
the statements re-run).

## Alternatives considered

- **Keep 100, rely on the coming NOTIFY push + idle gate** — the push fixes wake latency but the
  idle gate still costs per-lane work proportional to width; a right-sized keyspace helps both
  the current poll and the future push. Rejected as "later" — the polling cost is live today.
- **A non-divisor width (e.g. 8 or 10)** — 10 also divides 100; 8 does not and would need the
  hash in SQL or a Rust one-off migration. 5 vs 10 is a taste call at V0 scale; the product
  owner chose 5. Revisiting upward later needs the same divisor analysis in reverse (5 divides
  every multiple of 5, and a width INCREASE always needs the real hash — `partition % new` only
  works downward onto divisors).
- **Delete surplus lanes only, leave rows unstamped** — strands every in-flight and SCHEDULED
  row on lanes ≥ 5 that no consumer maps to anymore (the exact failure `partition.rs` warns
  about). Rejected outright.

## Consequences

- Idle mailbox queries: ~580k/hour → ~29k/hour on one instance. The NOTIFY-push + idle-gate
  follow-up (same shape as #301, `pg_notify` on `inbound_messages` insert) remains the real fix
  and also closes the up-to-10 s adapter→worker delivery latency on payment facts; this ADR only
  right-sizes the keyspace.
- A future width change is a MIGRATION, not a spec edit: downward onto a divisor is `partition %
  new`; anything else (including any increase) must recompute `stable_partition` for non-terminal
  rows in a one-off tool, and must remap rows BEFORE shrinking the registry.
- Tests that predict production stamps now use width 5; `stable_partition`'s golden-value tests
  keep width as a free parameter and are deliberately untouched.
