# Write-side authorization audit — every command, by how it authorizes

**Date**: 2026-08-17 · **Scope**: read-only audit, Phase 1 of a founder-directed plan. No source
code, spec or generated artifact was modified; nothing was committed or pushed.

**Question answered**: for each write-side command, what — if anything — compares the *caller* to the
*thing being acted on*?

---

## 0. Correction to the stated method — where the handlers actually live

The brief said the handlers are in `crates/domains/*/src/commands.rs`. **That path exists, but it
does not contain handlers.** The eight files under it are GENERATED type crates — `serde` structs for
the command payloads, emitted from `specs/{scope}/commands.yaml`, 993 lines across all eight, with no
`EventStore`, no `Actor` and no authorization of any kind:

```
// GENERATED by the Captain.Food codegen from specs/ordering/commands.yaml — do not edit by hand
crates/domains/ordering/src/commands.rs:1
```

The **real** handler surface is two files:

| File | What it holds | Handlers |
|---|---|---|
| `crates/application/src/commands.rs` | hand-written handlers + the shared `require_*` helpers | 86 of the 97 commands |
| `crates/application/src/generated/handlers.rs` | GENERATED "require + guard + append" handlers for the mechanical lifecycle commands | 9 commands |
| `crates/application/src/process_managers/refund.rs` | the two refund-decision commands, handled by `RefundProcess` | 2 commands |

`crates/application/src/commands.rs:157` re-exports the generated handlers, so every call site sees
one module.

**Consequence for the rest of the plan**: any step phrased as "edit `crates/domains/*/src/commands.rs`"
will edit generated payload structs and be reverted by the next `make generate`. The authorization
work belongs in `crates/application/src/commands.rs` (hand-written), in the codegen emitter behind
`crates/application/src/generated/handlers.rs`, or — per the compiler-first directive — in the
aggregate crates under `crates/domain/src/`.

## 1. The member-shaped owner — what `ScopeMembership` actually declares

**Declaration**: `specs/database/tables/projection_tables.yaml:1012` (`ScopeMembership`), with
`member_type` at line 1081.

Two things the brief's phrasing does not predict:

1. **There is no `MemberType` scalar.** `member_type` is typed
   `{ $ref: 'scalars.yaml#/UserType' }` — it reuses the platform role vocabulary
   (`specs/common/scalars.yaml:508`).
2. **`ScopeMembership` is a READ-side index.** Its own note says so ("the single index every
   read-side authorization question resolves against"), the table is marked `internal: true`, and
   grep confirms it: its only consumers are `crates/application/src/queries.rs:825`
   (`ScopeMembershipRepository`), the projector at
   `crates/application/src/projectors/scope_membership.rs`, and the subscription resolver at
   `crates/server/src/graphql/generated/subscription.rs:105`. **No write-side handler and no
   mutation resolver reads it.**

### Scope types it declares (`specs/common/scalars.yaml:721`)

| ScopeType | Meaning |
|---|---|
| `ORDER` | one order and everything hanging off it |
| `RESTAURANT` | one restaurant location |

### Member types it actually grants (`crates/application/src/projectors/scope_membership.rs:84-171`)

`UserType` has seven values; only four ever receive a row.

| member_type | Granted on | scope_type |
|---|---|---|
| `CUSTOMER` | `OrderPlaced` | `ORDER` |
| `RESTAURANT` | `OrderPlaced`; `RestaurantRegistered` | `ORDER`; `RESTAURANT` |
| `RESTAURANT_ACCOUNT` | `OrderPlaced`; `RestaurantRegistered`; `RestaurantListingClaimed` | `ORDER`; `RESTAURANT` |
| `RIDER` | `DeliveryAcceptedByRider` (revoked on `DeliveryCancelled` / `DeliveryDispatchFailed`) | `ORDER` |
| `ADMIN` | **never** — "the guard short-circuits on the role" | — |
| `PUBLIC`, `EXTERNAL` | **never** — absent from every grant rule | — |

**So exactly two aggregates have a member-shaped owner: `Order` and `Restaurant`.** Of the sixteen
aggregates that receive commands (`Cart`, `Catalog`, `Conversation`, `Customer`, `CustomerCredit`,
`DeliveryJob`, `DeliveryPartnerRegistration`, `MailboxSupervision`, `Order`, `PlaceOrderProcess`,
`Prospect`, `Reclamation`, `RefundProcess`, `Restaurant`, `RestaurantAccount`, `Rider`), fourteen
have no membership shape at all — including `Catalog`, `DeliveryJob`, `Reclamation` and `Customer`,
each of which is plainly owned by somebody in the domain.

## 2. Classification

### Category definitions used

- **(a) absent** — nothing in the handler compares the caller to the thing acted on. An existence
  load (`require_restaurant`, `require_catalog`, `require_cart`, `require_delivery_job`,
  `require_rider`, `require_restaurant_account`) rejects a *missing* aggregate, never a *wrong*
  caller, so it does not lift a command out of (a).
- **(b) payload-sourced** — the handler compares the aggregate's folded owner against an id **taken
  from the command payload**. The caller could have sent any value.
- **(c) context-sourced** — the handler compares against an id from the authenticated `Actor`.
- **(d) aggregate-borne** — an aggregate method decides, taking the actor id.

### Counts

| Category | Commands | Share of 97 |
|---|---|---|
| **(a) absent** | **82** | 84.5 % |
| **(b) payload-sourced** | **14** | 14.4 % |
| **(c) context-sourced** | **0** | 0 % |
| **(d) aggregate-borne** | **1** | 1.0 % |
| **Total** | **97** | |

Every one of those numbers is the row count of the corresponding block in §3 — count the rows.

**Denominator**: 97 = every message declared in `specs/*/actors.yaml` + `specs/*/processmanager.yaml`
whose `$ref` resolves into `commands.yaml`. The `commands.yaml` fragments declare 98 top-level items;
the 98th, `CartLine`, is a command value object no actor receives. 86 of the 97 are reachable through
a GraphQL mutation (`specs/*/api.yaml` `mutations:`); the other 11 are internal/PM-driven and carry
no mutation.

### `require_order` — the whole of the (b) order surface

`crates/application/src/commands.rs:1175`:

```rust
match state {
    Some(state) if state.restaurant_id == *restaurant_id => Ok((state, version)),
    _ => Err(reject("OrderNotFound", json!({ "orderId": order_id }))),
}
```

It has **12 call sites** — 5 in `crates/application/src/commands.rs` (lines 1199, 1222, 1247, 1275,
1318) and 7 in `crates/application/src/generated/handlers.rs` (lines 30, 50, 69, 88, 107, 127, 147).
Each call site is one command, so it serves exactly 12 commands: `RateOrder`, `RateRestaurant`,
`RecordDeliverySatisfaction`, `TipOrder`, `RequestRefund`, `AcceptOrder`, `StartPreparation`,
`MarkOrderReady`, `MarkOrderDelivered`, `RejectOrder`, `CancelOrderByCustomer`,
`CancelOrderByRestaurant`. The `restaurantId` it compares against is a payload field on all twelve
commands.

The remaining 2 of the 14 in (b) are the delivery pair, which compare the job's folded rider against a
payload `riderId`: `ConfirmPickup` (`crates/application/src/commands.rs:1423`) and `CompleteDelivery`
(`:1463`).

### (d) — the reference shape, and the search for others

`crates/domain/src/conversation.rs:56` `requires_post_message(state, actor_user_type,
actor_domain_id, author_role)` is the only aggregate method in the repository that takes an actor
identity and decides. `grep -rn "fn requires_" crates/domain/src/` returns exactly one hit, and
`actor.domain_id` appears in `crates/application/src/commands.rs` at exactly one live site (line
1908, the `PostMessage` call; the other, line 4078, is a test fixture setting it to `None`).

It is also only *half* enforced, by design and in writing (`conversation.rs:50-54`,
`specs/comms/actors.yaml:63-72`): the `CUSTOMER` arm compares `state.customer_id` to
`actor.domain_id`, while `RESTAURANT` / `RESTAURANT_ACCOUNT` return `Ok(())` unconditionally pending
the #144 identity bridge. `RIDER` is denied unconditionally.

## 4. What made the classification ambiguous

Ambiguity is reported, not resolved. Six things forced a judgement call.

**4.1 — `require_order` is shaped like authorization but is not one.** It compares a *payload*
`restaurantId` to the order's folded `restaurantId`, and rejects with `OrderNotFound`. Whoever can
guess or read an `orderId` can also send its `restaurantId` — the order's ref, restaurant slug and
tracking page all expose it — so the check keeps an honest restaurant off *another* restaurant's
order and stops nothing else. It is classified (b) rather than (a) because the comparison exists; it
should not be read as 12 commands being defended. The category (b) is really "a check whose input the
attacker supplies".

**4.2 — three checks look like ownership and are uniqueness.** `RequestEmailVerification:3525`,
`RequestPhoneChange:3576` and `ConfirmPhoneChange:3615` all read
`owner.customer_id != cmd.customer_id`. The purpose is `EmailAlreadyInUse` / `PhoneAlreadyInUse` — is
this contact already someone else's — and the guard fires only when a row exists. Nothing verifies
the caller *is* `cmd.customer_id`. All three are (a). A future automated classifier keying on
`!= cmd.*_id` would mis-file these three.

**4.3 — two checks look like ownership and are consistency.** `AddCartLine:937` and `PlaceOrder:2576`
compare a folded `restaurant_id` to the payload's. A cart has no owner before checkout
(`BindCartToCustomer` is the binding, and it too is unauthorized), so both are invariants, not
authorization. Both are (a).

**4.4 — `TipOrder` reads the actor and is still not context-sourced.** `commands.rs:1287` reads
`actor.user_type` to derive the `Tipper` business role. That is a *role*, not an *identity*: it never
asks whether this actor is a participant of this order. `TipOrder` is (b) via `require_order`, not
(c). Category (c) is empty in this repository — nothing anywhere compares `actor.domain_id` or
`actor.user_id` to an id on the aggregate except `PostMessage`, which routes it through the aggregate
and so is (d).

**4.5 — role-per-mutation does not subdivide any command here.** The brief anticipated a command
being in different categories per role. It never happens, because the category is a property of the
handler and the handler cannot see the role except in `PostMessage` and `TipOrder`. What role *does*
change is the blast radius: `markOrderDelivered` is `[RESTAURANT, RESTAURANT_ACCOUNT, RIDER]`, and the
RIDER path is (b)-checked only on the order's restaurant, so a rider principal who knows the pair
`(orderId, restaurantId)` can mark any order delivered. `addCartLine`, `removeCartLine` and
`changeCartLineQuantity` omit `roles:` entirely, which per `tools/codegen-rs/src/api.rs:549` and
ADR-20260720-191500 means **open to every role path** — the generated resolver carries no guard.

**4.6 — the write path has no per-instance layer at all, and the read path does.** Every mutation
resolver in `crates/server/src/graphql/generated/mutation.rs` carries exactly one guard,
`RoleGuard::new(ALLOW_…)`, which is a role check. The `ScopeMembership` index that answers "is this
principal a member of this instance" is consulted on reads and subscriptions only. So for 82 commands
the total authorization is: the caller reached the right role path. Whether that is "absent" or
"role-only" is a wording choice; under the brief's definition — *nothing compares the caller to the
thing acted on* — it is (a).

## 5. Findings worth carrying into Phase 2

1. **`PlaceOrder` is (a) and it moves money.** `customerId` is a required payload field
   (`specs/ordering/commands.yaml:116`, whose own description says "Resolved from the
   now-authenticated session"), and the handler writes it into `OrderPlaced` verbatim
   (`crates/application/src/commands.rs:2683`) with no comparison to the actor. The order, the
   payment and the resulting `ScopeMembership` grant are all keyed to a customer id the caller chose.
   Every downstream read-side guard then correctly enforces membership — of the wrong customer.
2. **The read side is strictly ahead of the write side.** `ScopeMembership` exists, is replicated to
   every read database, has a projector, a repository trait and tests. Phase 2 does not need a new
   index; it needs the write path to ask the question the read path already asks.
3. **`Actor.domain_id` is the missing input, and it is documented as missing.**
   `crates/application/src/ports.rs:18-24` says it is `None` for RESTAURANT and RIDER because the
   #144 bridge has not landed. Any context-sourced (c) design for those two roles is blocked on that
   bridge; CUSTOMER is not blocked — `PostMessage` already resolves it.
4. **Catalog is the largest undefended aggregate**: 13 commands, all (a). Twelve are
   `[ADMIN, RESTAURANT_ACCOUNT]`; `ImportCatalog` adds `EXTERNAL`. `require_catalog`
   (`crates/application/src/commands.rs:2862`) never asks which account owns the catalog, so any
   restaurant account that learns another's `catalogId` can edit its menu and stock.
5. **Compiler-first is available here.** `require_order` and the five existence-only helpers have
   identical shapes; a handler that cannot be written without supplying an authenticated principal —
   a witness type the mailbox worker mints from the envelope, rather than a `&Actor` the handler may
   ignore — would make the (a) category unspellable, which is a stronger outcome than 82 added
   checks.
