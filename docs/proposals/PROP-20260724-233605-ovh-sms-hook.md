## Why — and why SMS-only for V0 (the decision this records)

Phone OTP (the primary V0 login) delivers nothing today: Supabase has no Send-SMS hook, and OVH is
not a native Supabase provider (verified 2026-07-24 — the identity project has zero edge functions).
This wires it.

**SMS-only via OVHcloud, WhatsApp deferred** — the recorded decision, from a transparent cost review:
- **OVH SMS France** (screenshot-confirmed): **€0.06 HT/SMS** at 100, **€0.058** at 1 000 (3% remise);
  20 free credits for a new account.
- **WhatsApp auth France** (~$0.03–0.05 base) is **not meaningfully cheaper** in Europe (the big
  WhatsApp savings are India/Brazil), and once a BSP markup (can ~2×) or the mandatory SMS FALLBACK
  for the ~20% without WhatsApp is added, it can cost *more* — while adding a second channel, Meta
  onboarding, and template approval.
- The cost is **one SMS per customer lifetime** (verified at cart→checkout once, then the #112
  session persists), so the absolute spend is tiny and the engineering payback for a 2nd channel is
  years away at V0 Tours scale.
- **A separate UX case for WhatsApp is real** (not cost): higher delivery (~99% vs ~85–90% SMS),
  faster (~95% <3s), a one-tap copy-code autofill, and a verified-business trust badge, with claimed
  conversion lifts of +5–12pp in WhatsApp-heavy segments. **Caveat: the numbers are VENDOR-sourced**
  (companies selling WhatsApp OTP) — no independent study found — so treat magnitudes with caution
  and validate with our own A/B once we have volume. This UX angle, not cost, is the reason to keep
  WhatsApp on the roadmap.
- → WhatsApp is filed `post-V0` as a **UX-motivated** option (not a cost saving in France); this
  proposal ships SMS.

## Design — an OVH SMS client + the Send-SMS hook route (env-gated, fail-closed)

1. **`crates/infrastructure/integrations/ovh_sms.rs` — `OvhSmsClient`**: the OVH API v1 SMS send
   (`POST /sms/{serviceName}/jobs` `{ message, sender, receivers:[E.164] }`). OVH request signing:
   `X-Ovh-Signature = "$1$" + sha1_hex(APP_SECRET + "+" + CONSUMER_KEY + "+" + METHOD + "+" + URL +
   "+" + BODY + "+" + TIMESTAMP)` with `X-Ovh-Application`/`-Consumer`/`-Timestamp` headers.
   `from_env()` on `OVH_ENDPOINT` (base URL), `OVH_APPLICATION_KEY/SECRET`, `OVH_CONSUMER_KEY`,
   `OVH_SMS_SERVICE_NAME`, `OVH_SMS_SENDER` (default `CaptainFood`). Any missing → `None` (fail-closed).
2. **`POST /auth/sms-hook`** (in `crates/server/auth_routes.rs`, beside `/auth/*`): Supabase's Auth
   Send-SMS hook target. Verifies the **standard-webhooks** signature Supabase signs with
   (`webhook-id`/`webhook-timestamp`/`webhook-signature`, HMAC-SHA256 over `{id}.{ts}.{body}` with the
   base64 secret `SUPABASE_SMS_HOOK_SECRET`, ±5-min replay window, constant-time compare — the Stripe
   ACL pattern). Parses `{ user:{ phone }, sms:{ otp } }` → sends the OTP via `OvhSmsClient`.
   200 on success; a mapped error shape otherwise. Unconfigured (no secret / no OVH client) → 503.
3. **Composition root**: build the client + read the hook secret from env; inject into the route
   state. Absent → the route 503s (auth stays SMS-less, never a half-open hook).

## Verification

- **Unit**: OVH signature computation against a fixed vector; the standard-webhooks verify
  (valid/tampered/expired); the hook payload parse.
- **Live** (once the OVH account exists — free on the 20 credits): configure the Supabase Send-SMS
  hook → `/auth/sms-hook`, request a phone OTP, confirm the SMS arrives and `verifyPhone` succeeds
  end-to-end. This closes the last gap in phone login (#112 + #117 + this).
- `make rust` green.

## Home & migration

Built in captain-food now (fastest path, keeps #112/#117 live), but SMS delivery is company-wide auth
infra — it **migrates to the [captain-identity](https://github.com/TheCaptainCompany/captain-identity)
service** with the rest of auth ([its #1, step 3](https://github.com/TheCaptainCompany/captain-identity/issues/1)).

## Considered alternatives

- **Supabase edge function** for the hook (Deno, calls OVH) instead of an endpoint of ours: keeps the
  hook off our server, but splits auth logic into a third runtime (Deno) we'd otherwise not run, and
  is harder to unit-test in our workspace. Our Axum route reuses the Stripe ACL signature pattern and
  the existing adapter-route convention. Revisit if the hook migrates into the captain-identity
  service as an edge function there.
- **WhatsApp channel** (this proposal's headline deferral) — see §Why; `post-V0`.
- **Twilio** (the original spec wording) — rejected by ADR-20260722-174500 (OVH: FR price + EU
  residency); the wording was already corrected in #112's PR.
